## 项目、文件系统与 traceability

我们回顾一下上节课讲的是软件的项目管理。我们说项目是各种文件的集合，你的 intent、一些设计文档、你的 readme 都在你的项目里。所以我不喜欢那种 AI 写出来的非常非常长的 readme。对我来说，readme 应该就写一下你在设计这个项目的时候最初的初衷，你想做一个什么样的产品，这个产品能达到什么样的效果，可能可以有两个 screenshots，以及你最重要的那些设计。打个比方，有一天你突然想了一个非常好的点子，你真的想用它去挣一个亿，然后你想挣一个亿的时候你要组建一个创业团队，你要说服你那个 computer science 里面的人，比如你要说服我出来干，你其实只需要一个比较短的 readme，这是你的 intent，你想做这个东西。剩下比如我有架构的能力、我有写代码的能力，我可以把剩下的东西给你补出来。

*[06:13](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=373)*


你不需要知道这个软件系统是怎么样、它的 specification 是什么、它用什么样的数据库、怎么样支持用户从 1 到 10 到 100 到 100 万到 1 亿。你可能没有这个 computer science 的知识，但是你不需要有，你只要有那个最原始的设计，那 intent。然后再到 spec，就有我刚才说的一些：我要选什么样的数据库，我甚至要选什么样的编程语言，我的项目结构是什么，等等，小到每个模块的接口，都属于 spec。然后再到 code implementation，它现在都在这个项目里。有这样的项目以后，很自然地你就需要一个容器，把这些各种各样的文件管理出来。我们说大家用文件系统来管理项目，其实真的就是图方便。

*[06:51](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=411)*


因为你回到 1950 年、1960 年的时候，操作系统给你的存储功能就只有文件，它没有别的。那个时候关系型数据库还没有发明出来，所以所有的程序员别无他法，只能把你的项目以文件的形式存进来。所以这更多时候是一个历史的原因，历史是不停地往后涨、往后涨导致的原因。我自己是觉得，文件系统可能不是组织项目的正确方式，因为文件系统其实丢失了很多文件不适合表达的信息。有些信息其实是比较容易表达的，比如我的 intent、spec，我一条文档说这个地方我是怎么想的；或者这个测试用例是什么，我输入是什么，输出是什么，然后我要 assert 在程序运行过程中什么东西不能被违反。但是你马上就会发现，有很多隐藏的关联在项目里面是没有的。

*[07:49](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=469)*


我举个例子。你经常会在 AI 写代码的时候，现在 agent 会稍微好一点，有时候也不会。你让它说，把这个实现的方法从比如 linked list 换成更高效的 tree 结构去优化性能，这是很常见的：你突然发现性能不够了，然后你让 AI 去做，AI 就啪啪啪给你代码改了。但是你没有意识到的是，你可能在其中的某一个文件里写了一个文档，在 markdown 里写了一个“我这个项目是用 linked list 管理的”。在项目当中，你的文档和代码、测试之间就形成了一个关联。你写文档的时候可能还没有代码，所以你先写了那个文档，随手一写“这是个 linked list”，但是一旦你的代码实现了，这个关联又没有强行联系上。这就是一个技术债 technical debt。

*[08:56](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=536)*

![](assets/p10-f0005.jpg)


因为以后随着文档和代码不断向前推演，它们的不一致只会越来越多，不会越来越少，然后这个软件就陷入一个维护的泥潭。后面你拿出一段代码，甚至 AI 拿出一份代码，那到底是文档说的对还是代码说的对？你跟他聊天的那个历史没有了，你那个 chat 已经消失了，你换了一台电脑，你那个 git repo 里面可能还有一些 change 的日志，但是当你到最后的时候，你真的就不知道到底是代码对还是文档对。其实在软件工程里面，这是一个研究了非常非常长时间的问题，叫 traceability，可追踪性。你看这已经是 2014 年的时候他 review 的一些更老的文章，他就叫 software traceability。所谓的追踪，就是发现我们文件真的只是图保存在文件系统里方便，那么在一个软件项目当中，各种各样的测试用例、文档、哪怕中间一行代码，它们之间的关联是什么？我们能不能在软件系统的演进过程中仍然维持它？这其实是一个非常软件工程的问题。

*[10:23](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=623)*

![](assets/p11-f0011.jpg)


所以很多时候我们觉得蛮有意思的，文件系统将错就错了。那我们大家最后总有一天会发现，你用文件系统来管理代码，你受不了了，打个压缩包发布，打压缩包发布，然后打压缩包发给你的合作者，这件事情已经维护不下去了。所以就有了 SVN，有了 git。那下一个是什么？大家有没有想过下一个是什么？我今天一会儿会讲 Jujutsu，它可能是另外一个，甚至比 git 要好一些、更好用的版本控制工具。但我同时也觉得，刚才说到 traceability，其实如果以后我们再也都不写代码了，那软件他就不应该像现在这样，在 git repo 里面管理。我们现在有好多文件，什么 readme.md，然后是什么 hello.c，还有一个什么 docs 下的文档。

*[11:33](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=693)*


其实如果所有的这些东西我们人都不几乎不管了，那我们有没有可能——我一直在想，就等这个未来到来——把这里面软件或者部件之间，也许我们还是需要文档，但我们的文档可能是好多个切片，就把它们变成好多的对象 object 或者 entity。比如说这个文档和这个实现之间就有一个关系，这个代码实现了这个文档；然后我可能有个测试用例，这个测试用例也有这个文档，那这个文档和测试用例又关联起来了；然后这个测试用例是和这个代码的这部分实现关联起来的，然后这个文档又和这个文档是关联起来的。你看这是一个完全结构化的东西，没有办法在文件系统里以一个树状的形式表达，这是一个随便连接的图，有 cycle 的图 graph。那这个东西比如说我可以把它放到一个数据库里，叫 repo.db。

*[12:29](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=749)*


那显然人类就没有办法用现在的 UNIX 世界里面的工具去维护这样的一个 repository 了。但不要紧，我们应该怎么解决呢？用魔法打败魔法。人类理解不了的东西，我们只要训练 AI，它只要有强化学习的反馈信号，我们就可以训练 AI 能够理解这个 repo。所以我们要干的是什么呢？这就是一个非常大的项目，什么 Linux 内核、数据库，或者你们想做的一个价值一个亿的产品。好，那每次你就说，好 AI。因为你也不太可能一下子就说我要把这个产品直接变成另外一个产品了。当你比如说这个软件系统已经在工作了，那你一般来说就是要给它增加一个功能、修改一个功能，这就跟 git 的 philosophy 很像。

*[13:11](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=791)*


git 管理了文件、目录、快照和快照之间的关系。你的 git 希望我们能够小步前进：我每做一件事情，我 fix 一个 bug，我改一个文档，我都产生一个 commit。然后这样我就可以在多个人之间协作，每个人可以自己产生自己的 commit，然后我们可以用像 rebase、merge、fast forward 这些，或者是普通的 merge，来创建一个可追踪的整个项目的修改历史。那如果我们以后也不要文件，也许还可以用文件系统来管理，那我们要的就是我们可以让 AI 自动维护所有的 artifacts、软件 artifacts 之间的一致性。这个 artifacts 之间一致性，就比如说代码和文档必须要一致：我文档说这是 linked list，我的实现里面必须是 linked list；我的 test case 测试用例，我文档里面说我要有 ABC 三个方面的测试，那我这个 test case 就必须要有 ABC，它都是关联起来的。

*[14:23](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=863)*


然后从 git 里面我们知道我们希望小步前进。那同样的，当我们谈要做一小步的时候，其实我们知道这一小步是干什么的，所以你可以 chat，你可以跟 AI chat 说，我现在发现它有个 bug，或者我做了一个产品，比如我今天对这个幻灯片样式不满意，那这就其实是一个小步。这个时候一个大型的软件系统里面绝大部分的内容跟这个小步都是没有关系的。比如当我说我对这个幻灯片的样式不感兴趣的时候，大家可以看我的 repo，看下顶层的结构，我有一些 assets，甚至还有 .cache 缓存的系统，然后有 P1P2P3P4P5，然后有一些脚本等等。那任何一个软件系统当你只做一小步的时候，你就只需要看到这个软件系统的一小部分，大部分东西应该是无关的。

*[15:22](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=922)*


好，那既然是无关的，我们就可以让 AI 根据我们的 chat 把和我相关的东西给摘出来。它可以知道，哦，我现在需要的是这个文件、这个 test case 和这个文档，其实其他的东西都不需要了。然后你想 AI 有什么能力？AI 有动态生成任何内容的能力。everything is code，content as code，code 可以表达任何东西。所以 AI 可以根据我的 chat 生成一个和我要改的这一小步相关的 view，一个视图。你看你们学到的各种系统里面的概念还是有用的，因为不是所有的同学都学过数据库。数据库里面有一个叫 view 的概念，它说我们的数据就在这了，但我可以创建一个不一样的查询，可以把它以另一个形式展示出来，这就是这个很简单的想法。

*[16:20](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=980)*


我希望把这些数据以另外一个形式展现出来。比如当我看到的时候，我看到的不是这些代码、文档、DF，而是一个可视化的看板，然后这个看板上面大概列出和我这个小步相关的一些东西，然后问我要改什么。我改完了以后，同样的还是从一个 V0 到 V1。它还是一个 repo.db，但是这一小步就会把这些相关联的东西，比如说我要增加一种类型的测试用例，那它就会在这些地方加一些测试用例，这个地方加一些测试用例，有些地方可能要改掉。它就从一致的状态，各种错综复杂的关系，做一次小步的修改，到下一个版本。然后这样我们就好像软件工程就又变了，彻底变了。

*[17:18](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=1038)*


我觉得这是一个未来有可能发生的，就是在 AI 内部它是这样生产软件，然后从此以后我们也就再也不要看代码了。我觉得你们看到现在的这种现代 IDE，比如 cursor，我其实还蛮讨厌的，因为它现在打开默认就是 agent mode，然后 agent mode 就是原来的那个我们熟悉的 IDE 就没有了，强迫你用一个像 chat 的方式去跟它沟通。但因为我还是相对来说比较精通古法编程的，有时候我还是对代码有一些掌控欲，可能是不好的，可能是不对的，但是未来可能会是，这可能是一个途径。当然我觉得同学们肯定也会焦虑：如果未来这件事情真的有可能发生，而且可能一两年以后，大家就真的有一个公司把这东西做出来了，那我们学那么多东西还怎么办？

*[18:12](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=1092)*


其实你发现，在我们思考、创造这些东西的过程当中，我们用的都是你们学习的这些经典、集大成的 computer science 课程。我刚才说的数据库里的视图，我用的是借用了数据库的概念，实体和关系；然后我借用了 git。这个模型没有变。git 长期的开发经验说，我们要一步一步向前；如果在这个模型底下我们是大步向前，那就惨了。当然也有可能发生，就是模型非常非常强，一个非常大型的项目，一步啪就变成下一个了。这个怎么做，我们现在还不知道，但至少在初期，我们可能还是要沿用这个过去的、大家积累的软件工程智慧，去小步向前，然后通往那个极乐的世界。但我还是相信这个极乐世界确实有可能是能到的。

*[19:08](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=1148)*


所以这就引发了一个我觉得在大学里面蛮有意思的评论。这个同学应该是已经毕业了。因为我上节课说，我问同学们 git rebase，然后大家都不知道什么是 git rebase。他 raise 了一个 valid point，就是说学生时代大多数人是不会和他人共同合作的，也就是做作业，所以 rebase、merge 用的场景就很少。正确，这个 point 是对的。你们做作业的时候确实不会。然后我的回应大概是这样的：但是如果你真的去往外面的世界走一走，互联网开发者社区铺天盖地都是文档。所以你一定会有一天留意过别人的项目，会看到过叫 contributing.md，一般来说你马上就问这个。你们有没有同学问过？仓库根目录下的一份贡献者指南，通常回答我怎么参与这个项目。

*[20:27](https://www.bilibili.com/video/BV1Q6en6NEUo/?t=1227)*


你看它里面就有这些：项目的总体结构，然后分支、提交信息、PR 的规范和流程。如果你看过很多项目，比如随手打开看一眼，如果你发现里面东西都知道了，那你就知道了。如果你不知道，比如有一天你一定会看到一个项目里面说，你必须要在你自己的分支上 rebase，禁止你直接创建那种分叉的 merge，我们要保持线性历史，你就会知道 rebase 是干什么的。然后它现在是什么呢？现在我们的社会变得太快了，所以有一种学生其实——不是批评大家——因为你们上高中的时候就是这样的，在高中时候老师不教的就是你不需要会的，考试不考就是你不用学的。这是一个非常明显的、为了升学利益最大化的策略，这个是正确的，没有错。然后在你们到大学以后，如果你们还带着这个思维的话，你就会有这样的 gap，一种新人类和旧人类之间的 gap。

用最简单的方式帮你把，比如这个文件的学习资料的管理，学习资料的进入、通知消息的进入。就甚至到我现在，我自己回邮件的那 agent 都没有用任何的数据库。我的流程大概是这样的：我的那个 agent 会收我的邮箱，然后会把那个 email id 放到我的一个共享的云盘同步上，然后那个 email id 里面会有它的这个 AI 解析出来的，比如我回复的草稿，然后这个邮件的分类，是不是垃圾邮件，这种，然后然后再由下一级的流水线去处理。也就是说我先要明白的是我的系统里面有哪几级流水线，然后这几级流水线之间他们应该怎么协作，哪些东西通过云盘。就比如，那么因为我很喜欢我的云盘，是不是引入云盘要做一些架构的修改？我希望邮件和资料等都和云盘保持同步，这就叫需求的更改。我现在不知道它做的好不好啊，我让 agent 他帮我看一看。

也就是说什么是一个好的软件架构？你当然在当前时候，你是有需求的，这个现在实现可能是满足这个需求的，但是当你的需求发生变更的时候，你相应的做出的那个变化是摧毁性的，是背上一个技术债，还是别的，那就不知道了。然后我们来看一下他的这个设计，它有一个 assistant.db，他要把个人资料放到这里，邮件归档也放到这里，索引草稿仍然在 DB。现在看起来还不会引起很大的问题。因为绝大部分都是这样的，数据库确实应该不会引起特别大的问题，但是随着这个项目的不断进展，你就会发现，你有一种开发方式是这样：就是你上来就是一个大的，然后好几大步就把需求都实现完了，然后就拖着这个技术债不断地往后迭代，往后加功能，加功能；还有一个是你从最小的就得到一个特别精巧的架构。
